# План перевірок MVP

Це специфікація тестів пакета. Автоматизована частина лежить у папці `tests`.
Кожен результат фіксується як PASS / FAIL / BLOCKED / NOT RUN з версіями,
середовищем та доказом. Секрети й повні повідомлення не включати у звіт.

| ID | Сценарій | Очікуваний результат | Рівень |
| --- | --- | --- | --- |
| T01 | Docker відсутній або Engine зупинено | Зрозуміла причина та дія; готовність не показується | Автоматизований із підміною CLI + Windows |
| T02 | Перший запуск із валідними налаштуваннями | Стек готовий; один активний workflow; webhook зареєстрований | Інтеграційний + Windows |
| T03 | Дозволений користувач надсилає `Привіт` | Відповідь `Отримано: Привіт` | Telegram E2E |
| T04 | GET, зайвий шлях, редактор, API або test webhook через tunnel | Доступ відхилено; навчальна дія не виконується | HTTP інтеграційний |
| T05 | Немає webhook-секрету або він неправильний | Відхилено до виконання workflow | HTTP інтеграційний |

## Порядок підготовки тестів

1. До коду компонента створити відповідні test fixtures та виконувані перевірки
   його поведінки; спочатку зафіксувати очікуване падіння через відсутню реалізацію.
2. Для Telegram використовувати mock API та вигадані секрети; реальний бот —
   лише для окремого E2E після локального введення токена користувачем.
3. Для Docker використовувати окремий Compose project і тестові volumes;
   очищення не повинно видаляти дані студента чи чужі контейнери.
4. Після компонента запускати відповідні тести; після GUI — весь обов'язковий набір.
   Пропущені або заблоковані перевірки не вважати успішними.

## Поточні докази

Актуальні команди, версії, PASS, BLOCKED і межі кожного результату записані в
[VALIDATION.md](VALIDATION.md). Базовий Docker Linux-контейнер `hello-world` на
Windows-ПК користувача пройдено. Telegram E2E, WinForms і DPAPI restore не
позначаються PASS до запуску на цільовому Windows.
