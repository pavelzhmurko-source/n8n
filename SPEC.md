# Технічне завдання: локальний навчальний пакет AI-агентів

Версія 0.2 · 08.11.2026 · Статус: MVP реалізовано, триває приймання.

## Мета та платформа

Нетехнічний студент запускає локальний n8n через окреме вікно Windows,
надсилає текст Telegram-боту та отримує відповідь із навчального workflow.
Початкова відповідь: `Отримано: <текст повідомлення>`, без виклику AI-моделі.

Ціль: HP Pavilion 14-ce0064ur, Windows 11 Home 25H2, amd64, приблизно 8 ГБ RAM.
Docker Desktop, Compose та запуск Linux-контейнера вже підтверджено скриншотами.
Повний запуск, WinForms і споживання ресурсів потрібно підтвердити на цьому ПК.

## Обсяг MVP

| Компонент | Рішення |
| --- | --- |
| Середовище | Docker Desktop / WSL 2, Linux containers, Docker Compose |
| Автоматизація | n8n із SQLite та постійним volume |
| Code node | Офіційний external task runner тієї самої версії n8n |
| HTTPS | cloudflared Quick Tunnel; адреса може змінюватися |
| Публічний вхід | Мінімальний reverse proxy, лише дозволений POST webhook |
| Telegram | Webhook node n8n; окремий bot-сервер не потрібний |
| Інтерфейс | PowerShell + WinForms, українські підписи |
| Секрети | Профіль користувача поза Git; DPAPI для launcher; credentials n8n |

AI-моделі, macOS/Linux launcher, VPS, багатокористувацький режим, PostgreSQL
і queue workers не входять у MVP. Розширення описані в [архітектурі](ARCHITECTURE.md).

## Функціональні вимоги

1. Перший запуск пояснює залежності, приймає токен бота в маскованому полі
   та дозволений Telegram user ID; створення бота через BotFather — вручну.
   Необхідне початкове створення власника n8n допускається один раз.
2. Вікно містить «Запустити», «Зупинити», «Відкрити n8n», «Перевірити»;
   показує стани компонентів, адресу webhook та помилку з наступною дією.
3. «Запустити» перевіряє Docker Engine, порти й конфігурацію, запускає стек,
   чекає готовності, автоматично готує credentials і workflow та активує його.
   Студент не імпортує JSON вручну. Повторний запуск не створює дублікатів.
4. Реєстрація Telegram webhook виконується після готовності workflow та proxy;
   зміна адреси тунелю автоматично оновлює реєстрацію. Сторонній webhook
   не перезаписується без явного вибору користувача; pending updates не стираються мовчки.
5. Дозволений приватний текстовий запит повертає визначену відповідь.
   Інші типи подій і недозволені користувачі не запускають навчальну дію.
6. «Зупинити» завершує лише компоненти пакета, зберігає volume й секрети,
   не закриває Docker Desktop та не зачіпає чужі проєкти.
   Видалення webhook допускається лише після перевірки, що він належить цьому пакету.
7. Інтерфейс залишається чутливим під час запуску; повторне натискання не запускає
   паралельні операції. Очікування обмежені таймаутами з повідомленням про збій.
8. Окремі скрипти створюють узгоджену резервну копію бази й DPAPI-секретів,
   перевіряють її цілісність і відновлюють через staging та rollback volume.

## Захист і надійність

- Редактор n8n доступний лише через loopback; штатний логін зберігається.
- Публічно дозволено лише точний webhook-шлях і POST. Секрет заголовка
  `X-Telegram-Bot-Api-Secret-Token` перевіряється до виконання workflow.
- Неправильний секрет, метод або шлях відхиляються. Встановлюються межі
  розміру запиту та частоти; allowlist Telegram user ID перевіряється до дії.
- Секрети не потрапляють у Git, логи, експорт workflow або аргументи команд.
  Шифрування credentials не вимикається; ключ стабільний і резервується.
- Секрети передаються з DPAPI через короткочасні ACL-захищені файли. Bootstrap
  використовує офіційний CLI n8n. Auth не обходиться, БД n8n напряму не змінюється.
- Облік update_id зберігається між перезапусками. Успішно оброблений повтор
  не надсилає нову відповідь. Політика збоїв і повторів має бути документована:
  атомарна «рівно одна відповідь» між SQLite та Telegram API не гарантується.
- Версії образів фіксуються; TLS і перевірка цілісності залишаються ввімкненими.
- Автоматичне оновлення пакета не перезаписує змінений студентом workflow:
  власні навчальні зміни зберігаються; шаблон імпортується лише за відсутності.

## Результат і приймання

Постачання: README для студента, Compose, workflow-шаблон, launcher,
допоміжні скрипти, шаблони конфігурації без секретів, тести та інструкція відновлення.
Очікуваний запуск — подвійний клік без ручних команд після початкового налаштування.

MVP готовий після проходження обов'язкових сценаріїв [TEST_PLAN.md](TEST_PLAN.md)
і перевірки на цільовому Windows-ПК. Linux-перевірки не замінюють Windows GUI/E2E.
Повна система повинна виконати серію з 20 послідовних повідомлень без
падіння компонентів; використання пам'яті й час відповіді фіксуються в звіті.
Ціль відповіді — до 10 секунд за справної мережі, відхилення досліджуються.

Порядок виконання та умови переходу: [ROADMAP.md](ROADMAP.md).
